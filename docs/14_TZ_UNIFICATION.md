## 1. Проблема

Сейчас параметры функций задаются **разными способами**:


| Область                           | Как сейчас                                                                    |
| --------------------------------- | ----------------------------------------------------------------------------- |
| Большинство функций постобработки | Одна строка в колонке **C**, синтаксис у каждой функции свой                  |
| `сводная_таблица`                 | Вложенный диалог → **JSON** в C                                               |
| `ВПР`                             | Отдельный режим визарда → колонки **B–F**, не C                               |
| Функции с листами                 | `лист | параметры`, разделители `|`, `:`, `/`, `;`, `,` — **не единообразно** |
| Функции без листов                | Запятые, точки с запятой, `->`, `=`, `/` — **смешанно**                       |


В `param_wizard.py` кнопка **«Параметры…»** есть только для `сводная_таблица`; остальные функции редактируются вручную в C. Код диалогов сводной и ВПР (~1500 строк) живёт в `param_wizard.py`, что затрудняет сопровождение.

## 2. Цель

1. Для **каждой** встроенной функции постобработки диапазона, постобработки строки и финальной обработки — **вложенный микродиалог** с отдельной формой полей (как у сводной).
2. Код диалогов держать **в одном модуле**: `macro-lib/param_wizard.py` (как у `show_vlookup_param_dialog` / `show_pivot_table_param_dialog`), чтобы избежать проблем UNO с импортами/peer и циклических зависимостей. Допускается позднее вынесение в отдельный файл как рефакторинг, но **не является требованием ТЗ**.
3. Ввести **единый канонический формат** хранения параметров:
  - **JSON** (по умолчанию в диалогах, галочка «Сохранять как JSON» включена). JSON всегда это массив объектов, даже если по логике все оформлено как один объект - но при этом [ слева и ] справа можно не сохранять для читаемости - система должна понять при ошибке парсинга в лоб и подставить []; Если в итоге парсинга JSON он корректно парсится но не получается массив объектов, то критическая ошибка. Если JSON не парсится то пробовать парсить как строку с разделителями.
  - **текстовый** (разделители) — при снятой галочке, по **единым правилам**.
4. Парсеры в `libre_macros_lib.py` / `libre_macros_final_lib.py` должны понимать **оба** формата.

Старые форматы записи не обязательно поддерживать обратная совместимость нет требуется. Но надо переделать все генерации тестовых примеров.
5. **ВПР**: добавить JSON в С, **текущий формат B–F сохранить без изменений**.

### 3.4. Мультиблоки по листам — общий UI (`SheetBlockGrid`)

Для функций, где в C допускается **разный набор параметров на разных листах**, диалог строится по **единому шаблону**. Реализация — общие виджеты в `param_wizard.py` (не копировать разметку в каждый `show_*_dialog`).

#### 3.4.1. Два режима диалога


| Режим             | Код              | Когда                                                                              | Верхняя зона                    |
| ----------------- | ---------------- | ---------------------------------------------------------------------------------- | ------------------------------- |
| **Мультиблок**    | `SheetBlockGrid` | Параметры **зависят от листа** (толщина сетки, сортировка, зебра…)                 | Грид блоков + «+ Блок»          |
| **Список листов** | `SheetListPanel` | На перечисленных листах **одно и то же** действие (тонкая сетка, удаление листов…) | Чекбокс «Все листы» + грид имён |


Переключатель **«Одинаково на всех листах»** (в `SheetBlockGrid`):

- включён → грид скрыт, показывается **одна строка полей** без колонки «Лист»; в JSON/C — **один элемент массива без `sheet`**;
- выключен → режим мультиблока (грид).

#### 3.4.2. Грид блоков (`SheetBlockGrid`)

**Макет:**

```
☐ Одинаково на всех листах          ← master, по умолчанию выкл. в финале, вкл. допустим в range

┌──────────┬─────────────────────────────────────────────┬───┐
│ Лист     │ <поля параметров функции>                   │ × │
├──────────┼─────────────────────────────────────────────┼───┤
│ [Сводная▼]│ толщина [тонкая▼]  цвет [#CCCCCC    ]    │ × │
│ [Orders ▼]│ толщина [25      ]  цвет [темныйсиний▼]   │ × │
└──────────┴─────────────────────────────────────────────┴───┘
                        [ + Блок ]

── превью C (readonly) ─────────────────────────────────────
☑ Сохранять как JSON                    [ OK ]  [ Отмена ]
```

**Колонки грида (фиксированные + динамические):**


| №     | Колонка        | Тип                 | Описание                                                                                        |
| ----- | -------------- | ------------------- | ----------------------------------------------------------------------------------------------- |
| 0     | **Лист**       | Combo + ручной ввод | Имена листов **активной книги** (`doc.getSheets()`); пусто в range-режиме = «текущий лист шага» |
| 1…N−1 | *поля функции* | см. §6.1            | Задаются схемой `INNER_DIALOG_REGISTRY[fn_key].grid_columns`                                    |
| N     | **×**          | кнопка              | Удалить строку; минимум **0 строк** (пустой грид → параметры по умолчанию)                      |


**Кнопка «+ Блок»:**

- добавляет **новую пустую строку** в грид с фокусом в колонке «Лист»;
- дублирует значения **последней строки** (удобно: скопировать блок и сменить только лист);
- при первом открытии пустого диалога — **одна строка** с пустым листом и полями по умолчанию функции.

**Валидация при OK:**

- в режиме мультиблока: **имена листов в строках не должны пересекаться** (один лист — один блок); дубликат → подсветка строки и сообщение;
- пустая колонка «Лист» в range-постобработке допустима **только в одной строке** и означает «лист, на котором выполняется шаг»;
- в финальной обработке пустой «Лист» = «все листы книги» (как текст без `|`).

**Сохранение грида → JSON / текст:**

- **каждая строка грида** → **один элемент** корневого JSON-массива с полем `"sheet"` (если лист задан);
- **текст:** строки склеиваются через **DS_BLOCK** (`;`): `Лист1 | <параметры> ; Лист2 | <параметры>`;
- порядок строк в гриде = порядок элементов в массиве / блоков в C.

**Вложенные подтаблицы** (если у блока несколько однотипных правил):

- внутри строки грида или в отдельной панели под выбранной строкой — **второй грид** (пример: ключи сортировки, правила `формат_столбцы`);
- подтаблица сериализуется в **массив внутри JSON-объекта блока** (`keys`, `rules`, …), в тексте — через **DS_LIST** (`,`) внутри правой части после `|`.

API (черновик):

```python
def build_sheet_block_grid(dm, dlg, schema, initial_blocks, doc, *, allow_all_sheets=True):
    """
    schema.grid_columns — список колонок полей (id, label, kind, default, choices…)
    schema.nested_grids — опц. вложенные таблицы по id колонки-контейнера
    Возвращает controller: get_blocks(), set_blocks(), on_ok_validate()
    """
```

### 3.5. Постобработка диапазона vs финальная обработка (отдельный исполнитель)

Ключ в **`_FINAL_MAP_SPEC`** — только **регистрация** шага на листе «Финальная_обработка». Этого **недостаточно**: у range и final **разные сигнатуры** и контекст вызова.

| | Постобработка_Диапазон (RANGE) | Финальная_обработка (FINAL) |
|--|--------------------------------|-----------------------------|
| **Когда** | После копирования, **по каждому листу результата** в цепочке | После материализации сводных, **по всей книге**, до итогового диалога |
| **Сигнатура** | `(doc, sheet, data_range, header_row_range, *extra_args)` | `(doc, sheets, data_ranges, header_row_ranges, *extra_args)` — **коллекции** |
| **Колбэк в карте** | `merge_pp_range_*` ← `lm_pp_range_*` | `merge_final_*` ← **`lm_final_*`** (`libre_macros_values_lib.py` / `libre_macros_final_lib.py`) |
| **Фильтр листов из C** | Текущий `sheet` шага vs блоки `sheet` в `param_decode` | Обход всех пар `(sheet, data_range, header_range)`; блоки C выбирают листы и параметры |

**Нельзя** записать в `_FINAL_MAP_SPEC` тот же `merge_pp_range_*`, что в `_PP_RANGE_MAP_SPEC`, без обёртки — макрос не соберёт цепочку или вызовет с неверными аргументами.

## 4. Единый формат хранения

### 4.1. JSON (канонический)

Колонка **C** (или эквивалент для финала) — **всегда JSON-массив**, даже для одного блока:

```json
[
  {
    "v": 1,
    "fn": "раскрасить_блоки",
    "sheet": "Сводная",
    "key_columns": ["Отдел", "Город"],
    "colors": ["голубой", "#E2EFDA"],
    "sort": "asc"
  }
]
```

Правила:

- Корень — **только массив** `[...]`, не объект.
- Каждый элемент — объект с полем `"v": 1` и `"fn": "<ключ_B>"`.
- Несколько листов/блоков → **несколько элементов массива** (один элемент на лист).
- Пустые параметры → `[]` или `[{"v":1,"fn":"авто_высота"}]` (без `sheets` = все листы / без фильтра).
- Детекция JSON при чтении: строка после `strip()` начинается с `[` и парсится `json.loads` / `_lm_pp_parse_json_relaxed`.

**Миграция `сводная_таблица`:** сейчас в C — один объект `{...}`. Парсер принимает и объект, и `[{...}]`; диалог пишет только массив.

### 4.2. Текстовый формат (разделители)

Унифицированная иерархия (константы в `libre_macros_param_codec.py`):


| Уровень | Символ | Имя          | Назначение                                     |
| ------- | ------ | ------------ | ---------------------------------------------- |
| 1       | `|`    | **DS_SHEET** | Лист ↔ параметры блока                         |
| 2       | `,`    | **DS_LIST**  | Элементы списка (столбцы, имена листов, пары…) |
| 3       | `->`   | **DS_KV**    | Ключ → значение (альтернатива: `=`)            |
| 4       | `;`    | **DS_BLOCK** | Блоки (разные листы / разные задания)          |


Дополнительно (только где нужно, документировать в функции):


| Символ                | Имя           | Назначение                                                  |
| --------------------- | ------------- | ----------------------------------------------------------- |
| `/`                   | **DS_PAIR**   | Пара «заливка/шрифт», «толщина/цвет», «высота/выравнивание» |
| `%`                   | **DS_COLORS** | Несколько цветов в `раскрасить_блоки`                       |
| `!`                   | **DS_FLAG**   | Суффикс опции: `раскрасить_блоки` — `!граница` (§6.1); `формат_*` — `!конверт` / `!convert` → `convert_existing` (§6.1.1) |
| `|` (внутри значения) | **DS_FIELD**  | Поля структуры (как в ВПР: `Лист|Строка|Столбец|Заголовок`) |


**Шаблон блока с листом:**

```
<лист_или_список_листов> | <параметры_блока>
```

**Несколько блоков:**

```
Сводная | <параметры> ; Orders | <параметры>
```

**Без привязки к листу** (постобработка диапазона на текущем листе): один блок **без** DS_SHEET:

```
<параметры>
```

**Семантика «без листа» (обязательное общее правило для всех функций, где лист опционален):**

- **RANGE / ROW (постобработка), `SheetBlockGrid`:** если в блоке не указан лист (`sheet` в JSON отсутствует/пустой, или текст без `лист |`), то параметры применяются к **текущему листу шага** (тому `sheet`, который уже передан в `lm_pp_range_*` / `lm_pp_row_*`).
- **RANGE / ROW, `SheetListPanel`:** если `sheets` отсутствует / «Все листы» — **нет фильтра**: шаг выполняется на **каждом** вызове цепочки (на каждом листе результата, где он стоит в B); если `sheets` задан — только когда имя текущего листа в списке.
- **FINAL (финальная обработка):** если в блоке не указан лист / `sheets`, то параметры применяются ко **всем листам книги**, для которых в финале есть `data_range`/`header_row_range` (аналогично «пустому списку листов» в `тонкая_сетка`).
- Если лист указан явно (в JSON `sheet`, или в тексте `Лист | ...`) — шаг выполняется **только** на совпавших листах.

**Списки листов** внутри левой части: через DS_LIST (`,`), как сейчас `_lm_pp_parse_sheet_names_from_spec`.

**`sheet` vs `sheets` в JSON** (не смешивать в одном блоке):

| Поле | Паттерн UI | Смысл |
| ---- | ---------- | ----- |
| `"sheet": "Сводная"` | **§3.4.2** (`SheetBlockGrid`) | Один лист на **строку грида**; несколько листов — несколько элементов массива или `Л1,Л2 \| …` в тексте |
| `"sheets": ["Сводная","Orders"]` | **§3.4.3** (`SheetListPanel`) | Список листов в **одном** элементе массива; одинаковое действие на всех перечисленных |
| поле отсутствует | оба | §4.2: range — текущий лист шага; final — все листы с данными |

В **SheetListPanel** использовать только `sheets` (массив), не `sheet`. В **SheetBlockGrid** — только `sheet` на строку, не `sheets`.

Парсеры **сохраняют** поддержку старых вариантов (`:` вместо `|`, `/` вместо `|` для сетки, `,` между блоками при наличии `|`) — через слой `decode_param_legacy()`.

| Несколько листов с **одинаковыми** ключами | **DS_LIST** `,` слева от DS_SHEET | `Сводная,Orders \| Сумма -> -` |
| Ключи внутри блока | **DS_LIST** `,` | `Сумма -> -, Дата -> +` |
| Колонка ↔ направление | **DS_KV** `->`, `=` или `/` | `Сумма -> -` , `1/asc` , `ФИО=-` |
| Направление | `+`/`-`, `asc`/`desc`, `возр`/`убыв` (пусто = возр.) | `-> -` = по убыванию |
| Блоки для **разных** листов | **DS_BLOCK** `;` | `… ; Orders \| Дата -> +` |

**Без листа** (range: текущий лист шага; финал: все листы с данными) — только правая часть, без DS_SHEET:

```
Сумма -> -, Дата -> +
```

**Примеры целой строки C:**

| C | Смысл |
|---|--------|
| `Сумма -> -` | один лист / все листы — сортировка по «Сумма» убыв. |
| `Сумма -> -, Дата -> +` | два ключа на том же наборе листов |
| `Сводная \| Сумма -> - ; Orders \| Дата -> +` | разные ключи на разных листах |
| `Сводная,Итог \| Отдел -> +, Сумма -> -` | два листа — одинаковые ключи |
| `1:asc; ФИО=-` | без листа; альтернативные DS_KV (`:` и `=` внутри ключей, не путать с DS_SHEET — здесь нет `\|` / `:` между листом и ключами) |

Одна строка грида «Лист» в диалоге = один текстовый блок `лист \| ключи` (или только `ключи`, если «Одинаково на всех листах»).

**Параметр `outline_blocks` (выделить блоки толстой границей):**

- По умолчанию **`false`** — только заливка (и авто-цвет шрифта), как сейчас.
- Если **`true`**: для каждого **непрерывного блока строк** с одинаковым значением ключа (после опциональной сортировки) на внешнем прямоугольнике блока в пределах `data_range` (столбцы `sc…ec`, строки группы) рисуется **толстая** рамка.
- **`outline_color`**: имя или `#hex`; `null` / пусто — **авто**: цвет контрастирует с заливкой блока (та же логика, что `_lm_pp_colorize_auto_text_color`, но для линии границы — при необходимости затемнение/осветление заливки, не совпадать с `CellBackColor`).
- Толщина рамки — как у «толстая сетка» (**35**, 1/100 мм) или константа `LM_COLORIZE_BLOCK_OUTLINE_WIDTH` в коде.
- Граница только **внешний контур** блока (верх/низ/лево/право диапазона группы), не сетка внутри блока.
- Заголовок и служебная колонка-ключ не входят в оформление границей (ключевая колонка удаляется после шага, как сейчас).

**Текст по листам** (разделители §4.2):

```
[ <лист> DS_SHEET ] <столбцы_ключа> DS_KV <цвета> [ / <сортировка> ] [ !граница [ : <цвет_границы> ] ]
```

| Часть | Формат | Пример |
|-------|--------|--------|
| Лист (опц.) | `лист \|` или `лист:` | `Сводная \| …` |

| Несколько цветов | **DS_COLORS** `%` | `голубой%белый%серый` |
| Сортировка по ключу | `/+`, `/-`, `/asc`, `/убыв` (опц.) | `…/+`, `…/-` |
| Рамка блоков | **DS_FLAG** `!граница` или `!outline` | `…!граница`, `…/+!граница` |

##### §6.1.1. Конвертация текстовых значений (`convert_existing`)

**Проблема.** Назначение `NumberFormat` столбцу или ячейке **не меняет** тип содержимого: числа и даты, сохранённые как **текст** (в т.ч. с ведущим апострофом `'`), остаются текстом. Вручную это исправляется входом в ячейку (F2) и Enter. В UNO **нет** API, эквивалентного этому действию одной командой — нужна явная перезапись значения.

**Параметр** `convert_existing` (bool, опционально):

| Значение | Поведение |
| -------- | --------- |
| `false` / отсутствует | Только назначение `NumberFormat` (как сейчас в `lm_pp_range_format_*`) |
| `true` | Сначала конвертация подходящих текстовых ячеек в целевых столбцах, затем `NumberFormat` |

**Кодирование:**

- **JSON:** `"convert_existing": true|false` на уровне блока (элемента массива).
- **Текст:** суффикс **DS_FLAG** `!конверт` или `!convert` в правой части блока (после параметров листа), напр. `Сводная \| дата,срок !конверт`.
- **Диалог:** чекбокс с подсказкой: *«Преобразовать текст в число/дату перед форматом (аналог F2+Enter)»*.

**Область обхода:** строки `data_range` целевого листа, **без** строки заголовка (`header_row_range` не трогается). Пустые ячейки пропускаются.

**Алгоритм** (общий хелпер, напр. `_lm_pp_convert_cells_for_format`):

1. Для каждой ячейки столбца: если `CellContentType` = TEXT (или формула, дающая текст) — попытка преобразования; VALUE/DATE уже корректного типа — только `NumberFormat`.
2. **Число** (деньги, `#`, `0`, `%` в шаблоне): логика как в `lm_pp_row_convert_numeric_strings` — нормализация пробелов/запятой, `cell.String = ""`, `cell.Value = float`, затем формат. Строки, похожие на дату (`DD.MM.YYYY`, `YYYY-MM-DD`, с `:` для времени), **не** трогать в числовом режиме.
3. **Дата/время** (шаблон с `Д`, `М`, `Г`, `Ч`, `МИ`… или распознанный date-format): парсинг строки в serial LibreOffice (`cell.Value` как дата), затем формат. Нераспознанные строки оставить без изменений.
4. **Общий / неизвестный** формат: попытка числа, иначе даты, иначе пропуск.
5. Итог в лог постобработки: `конвертировано N`, `пропущено M`, `ошибка K` (по листу и столбцу).

**Реализация (рекомендации):**

- Переиспользовать и вынести из `lm_pp_row_convert_numeric_strings` парсинг числа в `_lm_pp_try_parse_number_string` / `_lm_pp_cell_set_numeric_value`.
- Добавить `_lm_pp_try_parse_date_string` (ru-локаль, основные литералы из `_LM_PP_DATE_FORMAT`).
- Пакетная запись по чанкам (`_LM_PP_COPY_ROW_CHUNK`) — как в `_lm_pp_apply_column_number_format_chunked`, чтобы не фризить UI.
- `XCellRangeData.setDataArray` — **не** использовать как единственный путь: смешанные типы и формулы в столбце ломают пакетную семантику.

**Связь с `преобразовать_числа` (ROW):** row-шаг остаётся для построчной обработки **всех** или выбранных столбцов **до** форматирования. `convert_existing` — встроенная конвертация **только** в столбцах, к которым применяется данный шаг `формат_*`; отдельный шаг `преобразовать_числа` для тех же столбцов при `convert_existing:true` **не обязателен** (но допустим — дублирование безвредно для уже числовых ячеек).

**Финал и range:** один и тот же флаг и хелпер; в `lm_final_format_*` — вызов через `_lm_final_apply_range_blocks`.

## 9. Критерии приёмки

1. У каждой функции из `_PP_RANGE_MAP_SPEC`, `_PP_ROW_MAP_SPEC`, `_FINAL_MAP_SPEC` с ненулевым C — есть запись в `INNER_DIALOG_REGISTRY` или явное «без диалога».
2. Функции с полистными параметрами используют `**SheetBlockGrid**` (§3.4.2) или `**SheetListPanel**` (§3.4.3); дублирования разметки грида в отдельных диалогах нет.
3. Диалог по умолчанию сохраняет **JSON-массив** в C; **одна строка грида = один элемент массива**.
4. Снятая галочка JSON даёт текст по правилам §4.2; round-trip без потери данных для тестовых кейсов из `05_POSTPROCESS.md`.
5. ВПР: B–F работают как раньше; JSON в C — опционально (§5).
6. Код диалогов — только в `param_wizard.py` (кроме тонких re-export в `pivot_table_wizard.py`).
7. Тестовые примеры и генераторы данных переведены на новые форматы.
8. Каждый ключ финала из `_FINAL_MAP_SPEC` вызывает **`lm_final_*`**, не `lm_pp_range_*` напрямую (§3.5).
9. Ключи **§3.5 B** из §6.3 зарегистрированы в `_FINAL_MAP_SPEC` и имеют `lm_final_*` (на момент сдачи — для всех запланированных B, не только A).
10. `sheet` / `sheets` в JSON соответствуют паттерну диалога (§4.2); смешение в одном блоке — ошибка кодека.

## 10. Принятые решения


| Вопрос                               | Решение                                                                                                                                                        |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ВПР JSON — куда писать               | Колонка **C** (§5.2)                                                                                                                                           |
| UI полистных параметров              | Общий `**SheetBlockGrid`** + `**SheetListPanel**` в `param_wizard.py` (§3.4)                                                                                  |
| Несколько листов в JSON              | **Один элемент массива на строку грида** (аналог блоков через `;` в тексте)                                                                                    |
| Порядок миграции                     | Сначала кодек + 5 частых функций, затем пакетами по 8–10                                                                                                       |
| Range vs Final | **Разные исполнители**: `lm_pp_range_*` vs `lm_final_*`; C и диалоги **общие** (§3.5). Запись в `_FINAL_MAP_SPEC` без `lm_final_*` **запрещена** |
| Листовые шаги без полей (§3.4.3) | **§3.5 B** для range-ключей (`авто_*`, `сброс_стрипов`, …) + **§3.5 A** для final-only (`вертикаль_центр`, `удаление_листов`); C = `sheets` или пусто |
| Оформление с параметрами в финале | **§3.5 B** — `lm_final_*` для `высота_строки`, `отступ`, `шрифт`, `ширина_столбцов`, `перенос*`, …; C = **§3.4.2** |
| Форматирование в финале | **§3.5 B** — `lm_final_format_*`; C с `sheets` (**§3.4.3** для `формат_деньги`) или `sheet` (**§3.4.2**); **`convert_existing`** (§6.1.1) |
| Текст в ячейках при `формат_*` | **`convert_existing`**: явная конвертация TEXT→VALUE/DATE перед `NumberFormat` (§6.1.1) |
| `sheet` vs `sheets` | **§3.4.2** → `sheet` на строку; **§3.4.3** → `sheets` в одном блоке (§4.2) |
| Без листа в блоке | **§4.2**: `SheetBlockGrid` — текущий лист (range); `SheetListPanel` — без фильтра (range) / все с данными (final) |
| Галочка JSON в диалоге ВПР           | По умолчанию **выключена**                                                                                                                                     |
| Галочка JSON в остальных диалогах    | По умолчанию **включена**                                                                                                                                      |
