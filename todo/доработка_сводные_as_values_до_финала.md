# ТЗ: материализация сводных `as_values` до финальной обработки

Доработка порядка выполнения финальной обработки книги при использовании `сводная_таблица` с `as_values: true`.

**Затронутая функция:** `сводная_таблица` (`Постобработка_Диапазон`) и зависимые от результата шаги `Финальная_обработка`.

**Проблемный сценарий:** после создания сводной с `as_values: true` выполнить финальный шаг, который ищет данные по заголовкам или обрабатывает диапазон листа, например `удалить_столбцы`.

**Цель:** финальные шаги должны видеть готовую таблицу сводной с обычными значениями и заголовками, а не внутреннее размещение ещё не материализованного DataPilot.

---

## 1. Проблема

При построении сводной `сводная_таблица` может отложить преобразование DataPilot в обычные значения до финальной стадии. В текущем порядке выполнения обычные шаги `Финальная_обработка` запускаются раньше этой отложенной материализации.

У живого DataPilot над данными находится служебная область `Filter`. Поэтому в момент выполнения финального шага первая строка листа ещё не содержит ожидаемые заголовки таблицы. Поиск столбца по маркеру не находит, например, заголовок сводной и в журнале появляется сообщение вида:

```text
Поставщики: нет столбца по маркеру «Количество - Код_товара»
```

После материализации таблица становится обычным диапазоном: строка заголовков оказывается в первой строке результата, и финальные шаги могут разрешить столбец по существующим правилам.

### Параметры воспроизведения

Постобработка диапазона:

```json
{
  "fn": "сводная_таблица",
  "sheet_name": "Поставщики",
  "row_fields": ["Поставщик"],
  "data_fields": [{"field": "Код_товара", "function": "COUNT"}],
  "as_values": true
}
```

Финальная обработка:

```json
{
  "fn": "удалить_столбцы",
  "sheet": "Поставщики",
  "markers": ["'Количество - Код_товара'"]
}
```

На другой локали LibreOffice может сформировать заголовок поля данных, например, как `Count - Код_товара`. Проверять и сопоставлять маркер следует по фактическим правилам поиска столбцов проекта; локализация подписи сама по себе не является причиной описанного сбоя порядка фаз.

---

## 2. Требуемое поведение

1. Все ожидающие сводные с `as_values: true`, созданные основным проходом постобработки до входа в общую `Финальная_обработка`, должны быть материализованы **до** запуска её обычных шагов.
2. Финальный исполнитель, получающий такой лист, должен видеть готовые значения и заголовки таблицы, а не служебную область DataPilot.
3. Шаги общей финальной обработки, которые используют лист, его заголовки, размеры или диапазоны данных (в частности, `удалить_столбцы`), должны работать по состоянию листа после материализации.
4. Если для исполнителей передаются предварительно собранные сведения о листах, диапазонах данных и строках заголовка, они должны оставаться корректными после материализации; при необходимости сведения следует обновить перед вызовом финальных шагов.
5. Сводные с `as_values: false` не должны материализоваться из-за этой доработки. Их текущее поведение и жизненный цикл DataPilot сохраняются.
6. Финальные шаги, не связанные со сводными, и текущие правила выбора листов/столбцов не должны измениться.
7. Удаление или скрытие листов остаётся заключительной операцией, чтобы не лишить более ранние шаги их целевых листов.

---

## 3. Требуемый порядок фаз

Для общей финальной обработки книги порядок должен быть следующим:

1. Очистить временные/мусорные листы, оставшиеся после создания сводных.
2. Материализовать накопленные к этому моменту сводные с `as_values: true`.
3. Выполнить обычные шаги общей финальной обработки, которым могут понадобиться итоговые заголовки и диапазоны листов.
4. Повторно очистить мусорные листы.
5. Выполнить отложенное разделение листов; его локальные follow-up шаги остаются в существующем `run_phase` и не являются основным сценарием данного ТЗ.
6. Повторно обработать очередь материализации, чтобы учесть сводные, появившиеся во время deferred split.
7. Выполнить заключительные операции макета и удаления/скрытия листов в их существующем порядке.

Материализация перед общими финальными шагами не отменяет повторную проверку/материализацию после deferred split. Это сохраняет обработку сводных, созданных на поздних фазах. Порядок локальных `after_final` callback-ов, запускаемых внутри follow-up разделения листов, этим ТЗ не меняется; если для такого callback будет воспроизведён аналогичный сбой, его следует отдельно включить в область доработки. Нельзя переставлять удаление и скрытие листов перед шагами, которые ещё могут к ним обращаться.

---

## 4. Область изменений

### Входит в задачу

- Переставить вызов существующей отложенной материализации в общей финальной фазе так, чтобы она завершалась до обычных финальных обработчиков.
- Сохранить обработку ошибок и журналирование, используемые существующей функцией материализации.
- Убедиться, что заголовки/диапазоны, передаваемые финальным исполнителям, соответствуют состоянию книги после материализации.
- Проверить обычный путь сбора и регрессию пути с deferred split, не нарушая текущую повторную материализацию и layout-фазу. Изменение локального порядка follow-up callback-ов внутри разделения листов не входит в задачу.
- Добавить краткое описание порядка выполнения в документацию по `сводная_таблица` и/или финальной обработке.

### Не входит в задачу

- Изменение алгоритма создания DataPilot или механизма преобразования сводной в значения.
- Принудительная материализация сводных, для которых указано `as_values: false`.
- Изменение локализации или формата заголовков агрегатных полей (`Count`, `Количество`, `Sum`, `Сумма` и т. п.).
- Изменение семантики маркеров, кавычек и поиска заголовков у `удалить_столбцы`.
- Переписывание исполнителей финальной обработки или общего пайплайна вне требуемого порядка фаз.

Если после перестановки фаз будет отдельно воспроизводиться несовпадение маркера с фактическим заголовком на конкретной локали LibreOffice, это оформляется и исправляется как отдельная задача сопоставления заголовков.

---

## 5. Требования к журналу

- Запись об успешной материализации каждой сводной должна появляться до записей обычных финальных шагов, работающих с соответствующим листом.
- При успехе финальный обработчик должен записать фактическое действие (например, `удалён столбец 2 «Count - Код_товара»`), а не пропуск из-за отсутствия заголовка.
- Ошибки материализации должны обрабатываться существующим способом. Нельзя молча считать лист материализованным и продолжать с заведомо неподходящей строкой заголовков.
- Для отложенного split сохранить отдельное журналирование повторной материализации, если она требуется.

---

## 6. Критерии приёмки

1. На сценарии из §1 журнал подтверждает порядок: сначала `Только_значения (сводные)`, затем финальный шаг `удалить_столбцы`.
2. В итоговом листе «Поставщики» целевой столбец сводной удалён, остальные столбцы и строки данных сохранены.
3. В журнале нет сообщения `нет столбца по маркеру` для заголовка, который соответствует столбцу по действующим правилам сопоставления.
4. Результат проверен при фактическом заголовке, который сформировал LibreOffice; не предполагать, что английское имя агрегата всегда переводится в русское или наоборот.
5. При `as_values: false` сводная остаётся DataPilot и автоматически не материализуется до финальных шагов.
6. При отсутствии сводных поведение и порядок остальных финальных шагов не меняются.
7. В сценарии с deferred split сохраняются текущие follow-up шаги, повторная материализация ожидающих сводных после этой фазы и заключительное удаление/скрытие листов; локальный порядок `after_final` callback-ов не изменён.

---

## 7. Проверка

### Ручной / интеграционный сценарий

На книге с исходным листом «Справочник_цен»:

1. Создать лист «Поставщики» сводной `COUNT(Код_товара)` по строковому полю «Поставщик», включив `as_values: true`.
2. В `Финальная_обработка` удалить столбец сводной по заголовку поля данных.
3. Выполнить сбор в LibreOffice/AlterOffice.
4. Проверить журнал, порядок фаз и конечный состав листа.

По возможности использовать headless-сбор существующего проекта на подготовленном шаблоне. Проверка должна включать не только код возврата раннера, но и итоговые ячейки/заголовки и релевантные строки журнала.

### Регрессионные сценарии

- Сводная `as_values: true` без финальных шагов.
- Сводная `as_values: false` с финальными шагами.
- Обычная книга без сводной.
- Сводная на листе, который затем удаляется/скрывается финальной обработкой.
- Отложенное разделение листов с финальной обработкой созданных листов; проверить отсутствие регрессии follow-up обработки, повторной материализации ожидающих сводных и layout-фазы.

Точка входа `collect_workbooks.py` не должна получать модульные присваивания, которые зависят от выполнения на уровне модуля скрипта: соблюдать ограничения AlterOffice 2026 для `Scripts/python/*.py`.

После правки entry-скриптов выполнить flatten и compat check по правилам проекта. Тестирование макросов — вручную в LibreOffice/AlterOffice; для воспроизводимого сбора допустим headless harness проекта.
