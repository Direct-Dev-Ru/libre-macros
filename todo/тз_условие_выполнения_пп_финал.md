# ТЗ: условие выполнения постобработки / финальной обработки

> **Статус:** черновик ТЗ (не реализовано).  
> Связано с: карта переменных (`__Карта_переменных.md`, `__карта_переменных_ручной_ввод.md`), лямбды (`__новый_столбец_как_лямбда_выражениею.md`, `__тз_субвизард_конструктор_лямбда.md`), визард параметров (`param_wizard.py`), codec JSON в колонке C.

Не отдельная `fn` постобработки, а **сквозной механизм gate** для строк:

- `Постобработка_Диапазон` / `Постобработка_Строка` / `Постобработка_xml`
- `Финальная_обработка`

Если условие **истинно** (или ячейка условия пуста) — шаг выполняется как сейчас.  
Если **ложно** — шаг **пропускается** (без ошибки), в журнале — пометка о пропуске.

**Где лежит условие:** колонка **D** для обычных codec-fn; для `функция_плагин` — исключение: колонка **E** (D занята `extra`).

---

## Цель

Дать возможность запускать один и тот же сценарий сбора по-разному в зависимости от:

- значения runtime-переменной (ручная / с листов источников / глобальная в карте);
- переменной среды ОС;
- имени пользователя ОС (список `IN`);
- произвольного булева выражения (лямбда с сахаром и `<<Переменные.…>>`).

Параметры условия задаются **отдельным визардом**; на листе — в **колонке D** (обычный fn) или **E** (плагин). Колонка C по-прежнему — только JSON / ref параметров функции (`fn`).

---

## Контраст с уже существующим

| Механизм | Что делает | Чем не является |
|----------|------------|-----------------|
| Префикс `__` в A | Отключает **всю** строку параметра навсегда | Условный gate по данным/среде |
| `sheet` / `sheets` в JSON C | На каких листах применять блок | Пропуск всего шага целиком |
| `условный_столбец` | IF/THEN по ячейкам таблицы → новый столбец | Gate запуска `lm_pp_*` / `lm_final_*` |
| **Условие в D/E (это ТЗ)** | Выполнять / пропустить **строку** pp/final | Не меняет данные само по себе |

## 1. Размещение на листе параметров

Лист группы `Параметры_Объединения*` / runtime `collect_params*`.

### 1.0. Обычный codec-fn

| Колонка | Роль |
|---------|------|
| **A** | Имя параметра (`Постобработка_Диапазон`, `Финальная_обработка`, …) |
| **B** | Ключ функции (`градиент`, `группировать_строки`, …) |
| **C** | JSON параметров функции (`param_encode` / `param_decode`) — **без** поля условия |
| **D** | JSON условия выполнения; **пусто** = условия нет, шаг выполняется всегда |
| **E+** | не используются для условия |

### 1.0b. Плагин (`функция_плагин`) — исключение: условие в E

Сейчас: B=`функция_плагин`, C=ref/JSON, **D=extra** (`_merge_pp_resolve_row_fn_and_extra`).

| Колонка | Роль |
|---------|------|
| **A** | Имя параметра pp/final |
| **B** | `функция_плагин` |
| **C** | ref / JSON плагина |
| **D** | `extra` плагина (**как сейчас**, не трогать) |
| **E** | JSON условия выполнения; **пусто** = условия нет |

Это **явное исключение** из правила «условие всегда в D»: у плагина D занята, условие сдвигается в E.

Хелпер чтения (логика реализации):

```text
condition_col = 4 if is_plugin(B) else 3   # E vs D (0-based)
raw = cell(condition_col)
```

Один и тот же JSON-контракт условия (§3) — отличается только колонка хранения.

### 1.1. Семантика пустой ячейки условия

- Ячейка условия (D или E) пуста / только пробелы → `when` отсутствует → **всегда выполнять**.
- Непустая, но JSON невалиден / неизвестный `kind` → **ошибка шага** (не молчаливый skip): в журнале явная причина; политика v1 — fail step (как битый C).
- Оценка условия = `False` → **skip** шага, журнал: `условие=False, шаг пропущен` (+ краткая сводка kind/полей).

### 1.2. Запись визардом

Сейчас `apply_param_value` для обычных pp **очищает D**. После внедрения:

- сохранение параметров функции (C) **не должно затирать** непустое условие (D у codec / E у plugin);
- сохранение plugin `extra` пишет **только D**, **не** затирает E;
- сохранение условия пишет **только** колонку условия (D или E); B/C/(D=extra) не трогает;
- копирование строк параметров (`copy_param_rows`) — копировать D **и** E вместе с C.

### 1.3. Покраска при «Вкл/выкл параметр» (`__` в A)

Меню: `toggle_merge_param_disabled` → `_param_apply_row_disabled_style` / `_param_apply_disabled_rows_styles`.

**Как сейчас:** ширина заливки = `_param_row_disabled_style_max_col` — в основном по подряд идущим заголовкам «Значение N» в строке 0 (+ особый случай legacy ВПР до col 5). Для `files` в `_param_row_max_col` учитывается хвост данных строки, **но в disabled-style этот хвост не берётся**. Итог: если в D/E есть текст, а шапка оборвалась на «Значение 2» (C), при отключении **D/E могут не покраситься**, при включении — не очиститься, если когда-то красились шире.

Известный соседний баг (ВПР JSON-only): лишняя покраска D–E шапки — см. `todo/__копирование_строк_параметров_и_визард_ВПР.md` §B.1; при реализации условия **не усиливать** этот баг.

**Требования v1 (обязательно проверить вручную):**

1. При записи условия в D (codec) шапка листа должна иметь как минимум «Значение 1…3» (B–D); при записи в E (plugin) — «Значение 1…4» (B–E). Расширять через существующие механизмы шапки / `_refresh_param_sheet_value_merges`, без legacy-подписей «Ячейка D/E».
2. `_param_row_disabled_style_max_col` (или аналог) должен покрывать **фактический** правый непустой столбец строки **и** колонку условия, если она задана:
   - codec + условие в D → max_col ≥ 3;
   - plugin + extra и/или условие в E → max_col ≥ 3 (D) / ≥ 4 (E).
3. Цикл вкл → выкл → вкл на строке с условием в D и на plugin-строке с D=extra + E=условие:
   - disabled: серая заливка `_PARAM_FILL_DISABLED` на A…условие (включительно);
   - enabled: фон D/E снова прозрачный, без «серого хвоста» и без покраски пустых столбцов правее нужды.
4. Регрессия: обычные строки без D/E (только A–C) — покраска как сейчас; JSON-ВПР без legacy B–F — не раздувать шапку/заливку до E «просто так».

## 2. Запуск визарда

Точка входа: `set_merge_param` / `_wizard_launch_plan` (`param_wizard.py`), меню «Мастер параметров».

Колонка условия: **D** (icol == 3) для обычного fn; **E** (icol == 4) для plugin.

### 2.1. Курсор в колонке условия

Если активный лист — лист параметров, строка — pp/final:

| Курсор | B | Действие |
|--------|---|----------|
| **D** | обычный codec-fn | сразу визард условия → писать в **D** |
| **D** | `функция_плагин` | **не** условие: D = extra (как сейчас / редактор extra при наличии) |
| **E** | `функция_плагин` | сразу визард условия → писать в **E** |
| **E** | обычный codec-fn | не колонка условия (игнор / main); условие только в D |

Аналогично текущему поведению C → субдиалог JSON/codec.

### 2.2. Курсор не в колонке условия (A / B / C / …)

Поведение как у основных параметров функций:

1. Основной визард параметра / субдиалог параметров функции (как сейчас для C / plugin).
2. В форме параметров функции **и** в форме plugin — кнопка **«Условие…»**.
3. По кнопке — тот же субвизард; после OK — записать в D (codec) или E (plugin); Cancel — без изменений.

Кнопка видна для всех pp/final (включая plugin). Hint: «колонка D» или «колонка E (плагин)».

### 2.3. Пустая / новая строка

Если A ещё не задан / new_param_mode — сначала основной визард выбора параметра и функции; условие — после того, как строка существует (кнопка «Условие…»). Прямой вход из D/E на пустой строке: подсказка «сначала выберите функцию».

## 3. Контракт JSON ячейки условия (v1)

Один объект (не список блоков fn). Хранится в **D** или **E** — формат одинаковый:

```json
{
  "v": 1,
  "fn": "условие_выполнения",
  "kind": "lambda",
  "expr": "lambda: str(<<Переменные.Филиал>>) == \"МСУЗ\""
}
```

Поле `fn` — фиксированный маркер codec/нормализации (`условие_выполнения`), **не** ключ карты pp.  
Синонимы kind в UI — русские подписи; в JSON — коды ниже.

### 3.1. Виды условий (`kind`)

| `kind` | Подпись UI | Смысл |
|--------|------------|--------|
| `lambda` | Лямбда | Булево выражение с сахаром / переменными |
| `variable` | Переменная runtime | Сравнение значения из карты переменных |
| `env` | Переменная среды | Сравнение `os.environ[name]` со значением или с глобальной/runtime-переменной |
| `os_user` | Пользователь ОС | Имя пользователя ОС ∈ списка |

Расширение v2: `and` / `or` деревья из нескольких узлов — **не** в v1 (в v1 достаточно одной проверки; сложная логика — через `lambda`).

---

### 3.2. `kind: "lambda"`

```json
{
  "v": 1,
  "fn": "условие_выполнения",
  "kind": "lambda",
  "expr": "lambda: \"<<Переменные.Регион>>\" in (\"Север\", \"Юг\")"
}
```

**Сигнатура v1:** выражение без строк таблицы результата (шаг ещё может идти до/вне конкретного листа).

- Предпочтительно: `lambda: <bool-expr>` (без аргументов) **или** голое выражение, которое компилятор оборачивает в `lambda: …`.
- Доступно:
  - подстановка `<<Переменные.…>>` **до** compile (как `expand_source_variables_in_lambda_code`);
  - helpers в namespace: сравнение строк (`tr` / strip), при необходимости тонкие обёртки `var("Имя")`, `env("NAME")`, `os_user()` — **желательно** в v1 для удобства без плейсхолдеров;
  - **не** обязателен sugar `rows` / `upd_rows` (нет текущей строки матрицы на этапе gate шага). Если пользователь вставит `rows(...)` — ошибка компиляции/вызова с понятным текстом.

Переиспользовать: `lm_sanitize_code_or_raise`, профиль сохранённых лямбд, по возможности `show_lambda_builder_dialog(..., kind="step_predicate")` (новый kind конструктора).

Ошибка в лямбде при оценке → fail step (не skip), журнал с traceback/кратким текстом.

---

### 3.3. `kind: "variable"` — сравнение с runtime-переменной

Источник значения — **runtime-карта** `_MERGE_SOURCE_VARIABLES_MAP` (уже после seed globals + ручной ввод + `Добавить_в_карту_переменных`). **Неважно**, откуда попала переменная: ручная, с листа источника, глобальная в карте.

```json
{
  "v": 1,
  "fn": "условие_выполнения",
  "kind": "variable",
  "name": "Филиал",
  "op": "eq",
  "value": "МСУЗ",
  "file": "",
  "sheet": "",
  "missing": "false"
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `name` | str | Логическое имя переменной (сегмент до `~` в ключе карты) |
| `file` / `sheet` | str | Опционально сузить поиск по сегментам ключа `имя~лист~файл` (маски как у карты: пусто/`*` = любой) |
| `op` | code | См. таблицу операторов |
| `value` | str | Правый операнд (литерал). Для `in` / `not_in` — список через `,` / `;` **или** JSON-массив строк |
| `compare_as` | `text` \| `number` \| `auto` | По умолчанию `text` (trim); `auto` — как в условном_столбце |
| `case_sensitive` | bool | Default `false` для text |
| `missing` | `false` \| `true` \| `fail` | Если переменная не найдена в карте: считать условие False / True / ошибка шага. **Default: `false`** |

Резольв значения: тот же lookup, что для `<<Переменные.Имя>>` / ручной карты (первый матч по маскам; при нескольких — первый по `_ORDER`, + warning в журнал).

---

### 3.4. `kind: "env"` — переменная среды

```json
{
  "v": 1,
  "fn": "условие_выполнения",
  "kind": "env",
  "env_name": "MERGE_PROFILE",
  "op": "eq",
  "rhs_kind": "literal",
  "value": "prod",
  "global_name": "",
  "missing": "false"
}
```

| Поле | Описание |
|------|----------|
| `env_name` | Имя переменной среды (`os.environ`); чтение через существующий `env_text` |
| `op` | Операторы как у `variable` |
| `rhs_kind` | `literal` — сравнить с `value`; `global` / `variable` — сравнить с текстом глобальной/runtime-переменной `global_name` (lookup через `lookup_global_text` / карту) |
| `value` | Литерал при `rhs_kind=literal` |
| `global_name` | Имя при `rhs_kind` ∈ {`global`,`variable`} |
| `missing` | Если env отсутствует или пуста: `false` / `true` / `fail` (default `false`) |

**UI:** combo `rhs_kind` («значение» / «глобальная переменная» / «переменная карты»); при выборе не-literal — поле имени вместо value.

---

### 3.5. `kind: "os_user"` — пользователь ОС ∈ списка

```json
{
  "v": 1,
  "fn": "условие_выполнения",
  "kind": "os_user",
  "op": "in",
  "users": ["ivanov", "petrov", "admin"],
  "case_sensitive": false
}
```

| Поле | Описание |
|------|----------|
| `op` | v1: только `in` и `not_in` |
| `users` | Массив имён **или** строка `user1,user2,…,userN` (разделители `,` / `;`, trim) |
| `case_sensitive` | Default `false` |

Имя ОС: существующий `os_username()` (`USERNAME` / `USER` / `LOGNAME` / `getpass`).

Сравнение: trim; при `case_sensitive=false` — casefold обеих сторон.

**Обязательный кейс UX:** подпись «Пользователь ОС входит в список», edit/combo накопительный список (как `columns_pick`, но свободный ввод имён) + × / ××.

---

### 3.6. Операторы (`op`) для `variable` / `env`

| Код | UI | Примечание |
|-----|-----|------------|
| `eq` | равно | |
| `ne` | не равно | |
| `contains` | содержит | только text |
| `not_contains` | не содержит | |
| `starts_with` / `ends_with` | … | text |
| `gt` / `gte` / `lt` / `lte` | сравнения | при `compare_as=number` |
| `in` / `not_in` | входит в список / не входит | правый операнд — список |

Для `os_user` — только `in` / `not_in`.

## 4. Когда оценивается условие

### 4.1. Момент gate

Оценивать **один раз на строку параметра** непосредственно перед вызовом обёрнутого `merge_pp_*` / `merge_final_*` (в wrap-callback / runner chain), когда runtime-карта уже заполнена:

1. seed globals;
2. ручной ввод в карту (если диалоги уже отработали для этой фазы);
3. `Добавить_в_карту_переменных` с источников (для шагов после сбора).

Для **ранних** шагов (до заполнения карты из источников): переменные с листов могут быть ещё пусты → срабатывает политика `missing`.

Финальная обработка и постобработка диапазона — один и тот же evaluator.

### 4.2. Не путать с фильтром листов

`sheet` / `sheets` внутри C по-прежнему решают, **на каких листах** применять блоки.  
Ячейка условия (D/E) решает, **вызывать ли функцию вообще**.  
Порядок: сначала условие (gate шага) → при True — обычный разбор C (+ D=extra у plugin) и фильтр листов.

### 4.3. Журнал

При skip:

```text
[условие] Постобработка_Диапазон / градиент: False (os_user not in […]) — шаг пропущен
```

При True (опционально verbose / debug): одна строка `условие=True`.  
При ошибке оценки — уровень ошибки, шаг не выполняется.

## 5. UX визарда условия

Окно ~520–600 px, в стиле остальных субвизардов; peer через `_nested_subdialog_create_peer`.

### 5.1. Макет

1. Заголовок: «Условие выполнения шага».
2. Краткая справка: «Пустое условие = шаг всегда выполняется. Сейчас редактируется колонка D» **или** «… колонка E (плагин)».
3. Combo **«Тип условия»** (`kind`) — подписи на русском.
4. Динамическая панель полей под выбранный `kind` (остальные скрыты).
5. Кнопки: **OK** / **Отмена** / **Очистить условие** (очищает D или E) / **Справка**.
6. Для `lambda`: edit + «Конструктор…» + pick сохранённых (как у других лямбд).
7. Для `variable` / `env`: combo имён (из известных globals / намёков карты, если доступны) + op + value / rhs.
8. Для `os_user`: накопительный список пользователей + op `in`/`not_in`.

### 5.2. Кнопка из основного визарда fn / plugin

В футере / панели формы: **«Условие…»**.  
Индикатор: если ячейка условия непуста — подпись «Условие… ✓» или hint «задано».

### 5.3. Нормализация

Модуль (новый или рядом с codec): `condition_decode` / `condition_encode` / `normalize_step_condition` — **только JSON**, по аналогии с `param_decode` (legacy-текст не поддерживать).

Константы UI (choices, labels) — в `pythonpath/*_cfg.py` (не в entry `param_wizard.py`).

## 9. Acceptance / ручная проверка (Calc)

1. **Пустая D (codec)** — любой `lm_pp_*` / `lm_final_*` как до изменений; визард fn не затирает заранее заданное условие в D при пересохранении C.
2. **Курсор в D** (codec) → сразу визард условия; OK → JSON в D; «Очистить» → D пуста.
3. **Курсор в C** → визард fn → «Условие…» → тот же диалог → пишет D.
4. **Plugin:** курсор в **E** → визард условия → пишет E; курсор в D → не условие (extra); сохранение extra не затирает E.
5. **os_user / in** — список из 2–3 имён; skip + журнал при чужом логине.
6. **variable** / **env** / **lambda** — как в исходном ТЗ (True / False / fail).
7. **Финальная_обработка** — те же kinds; codec → D, plugin → E.
8. **Вкл/выкл параметр** (§1.3):
   - строка codec с JSON в D: выкл → серые A–D; вкл → фон D снят;
   - строка plugin с D=extra и E=условие: выкл → серые A–E; вкл → D и E без серого хвоста;
   - строка только A–C без условия: покраска не шире нужного (нет лишней заливки пустых D/E).
9. После правок entry: `aoffice_flatten_defs.py` + `aoffice_compat_check.py`; версия в журнале.

## 11. Открытые решения (зафиксировать при реализации)

1. **Форма JSON:** строго один объект vs массив `[{…}]` — рекомендация: **один объект**.
