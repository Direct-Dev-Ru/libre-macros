# ТЗ: агрегат «Список_строк» для `сводная_таблица`

**Статус:** реализовано (v1, `3.10.347`).  
**Контекст:** визард «Параметры сводной таблицы» (`show_pivot_table_param_dialog`), исполнитель `libre_macros_pivot_lib.py`, постобработка/финал `сводная_таблица`.  
**Связано:** уже есть `as_values` (материализация DataPilot → статические значения) и отложенная фаза `merge_final_apply_pending_pivot_as_values`.

---

## 1. Назначение

Добавить в список агрегирующих функций сводной псевдофункцию **«Список_строк»** (`LIST_ROWS`).

**Смысл:** в ячейке области «Данные» сводной показать не числовую агрегацию (сумма/количество/…), а **текстовый перечень исходных строк**, попадающих под текущие ключи агрегации (поля строк / столбцов / фильтров), с выбранным набором колонок источника.

Формат **одной исходной строки** в ячейке:

```text
имя_колонки: значение | имя_колонки2: значение2 | … | имя_колонкиN: значениеN
```

Несколько исходных строк — **с новой строки** (многострочная ячейка):

```text
ФИО: Иванов | Отдел: Продажи | Сумма_руб: 1000
ФИО: Петров | Отдел: Продажи | Сумма_руб: 500
```

**Зачем:** в Calc DataPilot **нет** встроенной функции «вывести детальные строки». Нужен пост-проход после материализации сводной.

---

## 2. Ограничение API Calc и выбранный обходной путь

DataPilot (`com.sun.star.sheet.DataPilot*`) не умеет «список строк» как Function поля данных.

**Алгоритм v1 (обязательный):**

1. Пользователь выбирает функцию **Список_строк** и задаёт список колонок для вывода (`list_fields`).
2. Макрос **внутри** строит обычную сводную с функцией **Количество (`COUNT`)** по полю-счётчику (см. §4.2) — чтобы получить корректную раскладку ключей и ячейки «сколько строк попало в группу».
3. Включается / принудительно требуется **`as_values: true`** (уже реализовано: DataPilot → значения на листе).
4. После материализации для каждой **непустой data-ячейки** (где COUNT > 0) подставляется текст списка строк по ключам этой ячейки.

Шаги 2–3 уже есть в продукте; новое — шаг 4 + UI/JSON для `LIST_ROWS` / `list_fields`.

## 3. Где задаётся

| Место | Значение |
| ----- | -------- |
| Параметр | `Постобработка_Диапазон` / `Финальная_обработка` / `Постобработка_xml` — ключ `сводная_таблица` |
| Колонка C | JSON макета (как сейчас) |
| Визард | «Параметры сводной таблицы» — combo **Функция** + выбор полей списка |

Пример data-поля:

```json
{
  "field": "ФИО",
  "function": "LIST_ROWS",
  "list_fields": ["ФИО", "Отдел", "Сумма_руб"]
}
```

Полный фрагмент блока:

```json
{
  "v": 1,
  "fn": "сводная_таблица",
  "source_sheet": "Merge",
  "sheet_name": "Сводная",
  "as_values": true,
  "row_fields": ["Филиал"],
  "column_fields": [],
  "filter_fields": [],
  "data_fields": [
    {
      "field": "ФИО",
      "function": "LIST_ROWS",
      "list_fields": ["ФИО", "Должность", "Сумма_руб"]
    }
  ]
}
```

## 4. JSON / канон

### 4.1. Код функции

| | |
| - | - |
| Канон JSON | `LIST_ROWS` |
| Подпись в визарде | `Список_строк` |
| Синонимы при разборе | `список_строк`, `list_rows`, `LIST`, `детализация`, `detail_rows` |
| Регистрация | добавить в `_PIVOT_DATA_FUNCTIONS` (`libre_macros_param_wizard_cfg.py`); **не** маппить на UNO Function — это псевдокод |

В DataPilot на этапе создания сводной `LIST_ROWS` **заменяется** на `COUNT` (см. §5).

### 4.2. Поле `field` в `data_fields[]`

Как у обычных мер: имя колонки источника, по которой Calc считает **COUNT** (служебный счётчик для раскладки).

**Правила выбора (визард + исполнитель):**

1. Предпочтительно — поле из `list_fields[0]`, если оно **не** входит в `row_fields` ∪ `column_fields` ∪ `filter_fields`.
2. Иначе — любое доступное поле источника, не входящее в ключи агрегации.
3. Если таких нет (все колонки — ключи) — взять первое доступное поле источника; COUNT по нему всё равно даст число строк группы.
4. В UI подпись в списке «Данные»: `Список_строк — <field>` (аналог `Количество — ФИО` на скрине).

### 4.3. `list_fields` — колонки детализации

| | |
| - | - |
| Канон | `list_fields` |
| Синонимы | `detail_fields`, `detail_columns`, `поля_списка`, `колонки_списка` |
| Тип | JSON-массив строк (имена заголовков источника) |
| Обязательность | да при `function=LIST_ROWS`; пустой / отсутствует → ошибка визарда / `report.problem` и **не** подставлять детализацию (оставить COUNT как число) |
| Порядок | порядок вывода слева направо в строке детализации |

Допустимы поля, которые уже стоят в строках/столбцах/фильтрах (для читаемости списка), и поля только из «доступных».

### 4.4. Совместимость с `as_values`

| Правило | |
| ------- | - |
| При наличии хотя бы одного `LIST_ROWS` в `data_fields` | `as_values` **принудительно true** (как в `Постобработка_xml`) |
| Визард | checkbox «Как значения» checked + disabled с подсказкой: «Список_строк требует материализации» |
| Сериализация | всегда писать `"as_values": true` |

### 4.5. Несколько data-полей

v1: **не более одного** `LIST_ROWS` в одном блоке сводной.

- Если в массиве несколько — визард предупреждает; исполнитель берёт **первый** `LIST_ROWS`, остальные игнорирует с записью в журнал.
- Обычные SUM/COUNT/… вместе с `LIST_ROWS` в v1 **не поддерживать** (усложняет поиск data-столбца после материализации). Визард: при выборе Список_строк очищать остальные data-поля или блокировать добавление второй меры.

## 5. Алгоритм исполнителя

### 5.1. Создание сводной

Вход: config с `data_fields[].function == LIST_ROWS`.

1. Нормализовать config: `as_values=true`, `function` для DataPilot → `COUNT`, сохранить оригинал в служебном ключе, напр. `_list_rows_meta`:

```json
"_list_rows_meta": {
  "count_field": "ФИО",
  "list_fields": ["ФИО", "Должность", "Сумма_руб"],
  "active": true
}
```

(ключ с `_` можно не писать в ячейку C из визарда — держать только в runtime / либо писать канон `list_fields` в data_fields и восстанавливать meta при разборе).

2. Построить DataPilot как сейчас (`lm_pp_range_pivot_table` / create path).
3. Зарегистрировать лист в `as_values` pending.

### 5.2. После материализации (`as_values`)

Точка встраивания: после успешного `lm_values_pivot_exists` / `lm_pp_pivot_post_values_format` (или отдельный шаг в `merge_final_apply_pending_pivot_as_values` / `_merge_run_pending_pivot_as_values`), **до** follow-up постобработки материализованных листов.

Для листа с `_list_rows_meta.active`:

1. Определить на материализованном листе:
   - столбцы ключей строк (из `row_fields`, tabular layout);
   - столбцы ключей столбцов (из `column_fields`, если есть);
   - столбец(цы) данных COUNT (область данных).
2. Для каждой data-ячейки:
   - прочитать число `n` (COUNT); если пусто / 0 / «Итого»/grand total → **не трогать** или очистить по политике §7;
   - собрать словарь ключей группы из заголовков строк/столбцов этой ячейки;
   - отфильтровать строки **листа-источника** (`source_sheet` + header/data range из config) по равенству ключей;
   - отформатировать до `n` строк (фактически все совпавшие; если совпавших ≠ n — warning в журнал);
   - записать **многострочный текст** в ячейку (`String`, с переносом); NumberFormat → текст при необходимости.
3. Включить перенос текста / авто-высоту для data-столбца (или опереться на уже существующий `post_values_format` + опциональный вызов `перенос_и_авто_высота` только для data-колонок) — v1: хотя бы `IsTextWrapped=True` на диапазоне данных.

### 5.3. Сопоставление ключей

- Сравнение значений: как текст после `strip`, без учёта регистра **опционально**; v1 — **как отображаемый текст ячейки** источника (через тот же helper, что для CTC/снимков, либо `String`/`Value`→текст).
- Пустой ключ: отображать как пустую строку; строки источника с пустым тем же ключом входят в группу.
- Фильтры страниц (`filter_fields`): учитывать выбранные в сводной значения; если после as_values фильтры «свёрнуты» в статику — ключи фильтров уже отражены в видимой таблице; для выборки из источника применять **все** page-поля из config как дополнительные равенства, если их значения однозначно читаются с листа; иначе — только row+column ключи (зафиксировать в логе).

**Рекомендация v1:** матчить только **row_fields + column_fields**; `filter_fields` считать уже учтёнными раскладкой (пользователь задаёт фильтр при построении). Если page-фильтр оставляет один срез — источник всё равно полный: тогда **нужно** применять filter_fields к источнику. Итого v1: **row + column + filter** все три, значения filter брать из config snapshot на момент build (сохранить выбранные page items в meta при создании, если API позволяет; иначе читать с материализованного листа).

Практичный минимум v1 для типового кейса со скрина (только `row_fields=["Филиал"]`, без column/filter):

- ключ группы = значение в столбце «Филиал» текущей строки сводной;
- фильтр источника: `Филиал == ключ`.

### 5.4. Форматирование строки детализации

Для каждой исходной строки, в порядке появления в источнике (сверху вниз):

```
join(" | ", [f"{name}: {value_text(name)}" for name in list_fields])
```

- `value_text`: пусто → пустая строка после `: ` (т.е. `Код: `).
- Даты/числа — как отображаемый текст (или короткий канон `DD.MM.YYYY` / число без лишних нулей); v1 достаточно unicode/str снимка ячейки.
- Разделитель полей: ` | ` (пробел-пайп-пробел).
- Разделитель записей: `\n` (LF).
- Имена колонок — **как в заголовке источника** (не транслит).

Константы разделителей — в `pythonpath` cfg/pivot_lib, не в entry.

### 5.5. Производительность

- Наивный O(ячейки_сводной × строки_источника) допустим для типичных Merge (сотни–тысячи строк).
- При `rows_source > 50000` или `cells_data > 5000` — один раз построить индекс `tuple(keys) → [row_indices]` по источнику, затем O(1) lookup.
- Лимит строк в одной ячейке (защита): `list_rows_max_per_cell` default **200**; хвост заменить строкой `… ещё N строк`; константа в cfg, опциональный JSON-ключ backlog.

## 6. Визард

### 6.1. Combo «Функция»

Добавить пункт **`Список_строк`** в `_PIVOT_DATA_FUNCTIONS` (в конец списка или после «Количество»).

При выборе и нажатии `-> Данные`:

- в `LbData` попадает метка вида `Список_строк — <имя_поля>`;
- поле берётся из текущего выделения в «Доступные поля» (как сейчас для SUM/COUNT).

### 6.2. Выбор `list_fields`

Когда в «Данные» есть элемент с Список_строк (или при выборе функции Список_строк):

**Вариант A (рекомендуется для UX):** отдельный listbox / multi-pick **«Поля списка»** под блоком Данные:

- источник — те же заголовки, что «Доступные поля»;
- накопительный выбор (как `columns_pick`): combo + `×` / `××`;
- при OK пишется в `list_fields`.

**Вариант B (минимальный):** по кнопке «Поля списка…» субдиалог с checklist.

v1: достаточно **A** или **B**; не смешивать с CSV-параметрами.

Default `list_fields` при первом добавлении Список_строк:

- если в «Доступные» есть поля не из ключей — взять до 3 первых таких;
- иначе — `[field]` счётчика.

### 6.3. Поведение checkbox as_values

См. §4.4.

### 6.4. Отображение в LbData

Парсер метки ↔ JSON: расширить `_pivot_data_field_label` / `_pivot_parse_data_field_item` для `LIST_ROWS` и при сериализации сохранять `list_fields` из отдельного контрола (не кодировать list_fields в текст listbox).

## 7. Краевые случаи

| Тема | Правило v1 |
| ---- | ---------- |
| Grand total / «Итого» / «Result» | Не заполнять Список_строк (оставить число COUNT или очистить data в total — **оставить число**) |
| COUNT = 0 | Ячейку не переписывать |
| Не найдено строк в источнике при COUNT>0 | Warning в журнал; ячейку не трогать или писать `(нет строк источника)` — предпочтительно warning + оставить COUNT |
| Нет `list_fields` | Не подставлять детализацию; problem в отчёт |
| Источник переименован / лист не найден | Как у обычной сводной — ошибка build |
| `column_fields` непустые | Поддержка обязательна: ключ = row-ключи ∪ column-ключ(и) заголовка data-столбца |
| Несколько уровней row_fields | Все уровни участвуют в ключе (tabular layout уже даёт столбцы) |
| Спецсимволы `\|` и `:` в значениях | v1 не экранировать (документировать); backlog — кавычки |
| xml_excel_ods / Постобработка_xml | Тот же JSON; as_values и так true — пост-заполнение Список_строк выполнять в UNO-фазе после материализации xml-сводной, если путь общий |

## 9. Критерии приёмки (ручная проверка в Calc)

Автотесты не писать.

1. **Визард:** в combo функций есть «Список_строк»; можно задать `list_fields`; as_values включается автоматически.
2. **JSON в C** содержит `"function":"LIST_ROWS"` и `"list_fields":[...]`, `"as_values":true`.
3. **Сценарий как на скрине:** строки = `Филиал`, данные = Список_строк по полям например `ФИО`, `Должность`, `Сумма_руб` — на листе сводной в data-ячейках многострочный текст вида `ФИО: … \| Должность: …`, группы по филиалам совпадают с фильтром источника.
4. **Порядок** строк в ячейке = порядок на листе-источнике.
5. **Итого** не превращаются в списки.
6. **Обычные SUM/COUNT** без регрессии (функция не Список_строк → путь как сейчас).
7. **Журнал:** при LIST_ROWS видны фазы COUNT→as_values→подстановка списка (debug/stat).

## 10. Вне объёма (v1)

- Несколько `LIST_ROWS` / смесь с SUM в одной сводной.
- HTML/Rich text, гиперссылки, отдельные ячейки на каждую деталь.
- Экспорт list_fields в xml без UNO-фазы (чисто файловая подстановка).
- Настраиваемые разделители в UI (только константы/JSON backlog).
- Сортировка детальных строк внутри ячейки (кроме порядка источника).
- Pytest.
