# ТЗ: копирование строк параметров + доработка визарда ВПР

Два связанных блока изменений UX листа параметров сбора (`Параметры_Объединения*`):

1. **Макрос копирования строк параметров** — безопасное дублирование выделенных строк с учётом уникальности параметра и «мягкой» вставкой без лишних `insertRows`, если снизу уже есть пустые строки.
2. **Визард ВПР** — убрать legacy-артефакты UI/оформления заголовков; заменить пару «начало строки / столбец / заголовок» на явные диапазоны левой/правой таблицы; добавить тип соединения (левое / полное) и зеркальный набор колонок для полного join.

**Цель:** ускорить правку сценариев на листе параметров и сделать форму ВПР понятнее, без наследия «ячеек B–F» в подписях и без ложной раскраски колонок при JSON-режиме.

**Документация (обязательно по итогам внедрения):** концептуальные изменения отразить в docs — **без** подробного описания пиксельной вёрстки визарда (только смысл полей, семантика диапазонов, join, поведение макроса копирования).

## Часть A. Макрос копирования строк параметров

### A.0. Назначение

Макрос на листе параметров сбора: **скопировать текущую строку (или выделенный диапазон строк) и вставить копию(и) ниже**, раздвигая содержимое при необходимости, с запретом копирования **уникальных** параметров.

Не путать с:

- `копирование_диапазонов` / `копировать_лист` — работа с книгой **результата**;
- копированием строк в `todo_task` — другой домен (лист задач).

### A.1. Точка входа и размещение

| Элемент | Требование |
| ------- | ---------- |
| Entry | Тонкая обёртка в `Scripts/python/` (например `copy_param_rows.py`) + логика в `pythonpath/` (`libre_macros_*_lib.py` / cfg) |
| Меню | `CONTEXT_CELL_MENU` — пункт вроде «Копировать строку(и) параметров» (уровень рядом с другими утилитами листа параметров) |
| Вызов | Активная ячейка / выделение на листе `Параметры_Объединения*` (и алиасы имён листа параметров) |
| AO 2026 | Константы и XML — только в `pythonpath/`; flatten defs + `aoffice_compat_check` после правок entry |

Имя экспортируемой функции и ключ меню — зафиксировать при реализации; в журнале / msgbox — русские формулировки.

### A.2. Принцип работы

1. Определить **набор исходных строк** (1-based или 0-based единообразно с остальным кодом листа параметров):
   - если выделена **одна** ячейка / одна строка — копируется эта строка таблицы параметров;
   - если выделено **несколько строк** (непрерывный или дискретный selection — см. §A.4) — копируются **все** выделенные строки параметров **в исходном порядке сверху вниз**.
2. Для **каждой** копируемой строки прочитать имя параметра в колонке A (каноническое имя через `param_canonical_sheet_name` / аналог, с учётом `__` отключения).
3. Проверить **уникальность** (§A.3):
   - если среди копируемых есть хотя бы один уникальный параметр — **весь** копирующий прогон **отменяется** (ничего не вставлять), показать сообщение (§A.5);
   - опционально v1: при смеси уникальных и неуникальных в выделении — тоже полная отмена (проще и предсказуемее).
4. Определить **якорь вставки**: сразу **под последней** строкой копируемого блока (после max(row) выделения).
5. Оценить, сколько **пустых** строк уже есть начиная с якоря вниз (§A.6):
   - если пустых строк **≥ N** (N = число копируемых строк) — **не** вызывать вставку строк таблицы; записать копии в уже пустые ячейки;
   - иначе вставить недостающие строки (`Rows.insertByIndex` / эквивалент) **перед** первой непустой строкой ниже / в позицию якоря так, чтобы существующие непустые строки **съехали вниз**, а не затёрлись.
6. Скопировать **все используемые колонки** строки параметров (A…max used / до объединённого «Комментарий» — как принято при записи визардом; минимум A–F с учётом ВПР legacy B–F), включая значения, по возможности оформление (best effort; если оформление падает — значения всё равно копировать, в лог/msg — предупреждение).
7. После вставки восстановить заголовки строки 1 листа параметров при необходимости (`_restore_param_sheet_header_row` / аналог), чтобы не оставить legacy-метки «Ячейка B»… от ВПР.

### A.3. Уникальные vs повторяемые параметры

Источник истины — каталог визарда (`_build_param_catalog` / `multi_row` в `param_wizard.py` + cfg):

| `multi_row` | Поведение при копировании |
| ----------- | ------------------------- |
| `False` | **Уникальный** — копировать **нельзя** |
| `True` | Можно дублировать (как сейчас несколько строк `Постобработка_*`, `ВПР`, `Ячейка_В_Столбец`, …) |

Типичные уникальные (не исчерпывающий список — брать из каталога на момент реализации): `Режим`, `Файлы-Источники`, `Начало_Строка`, `Строка_Заголовков`, `Отображение_прогресса`, флаги `MERGE_*`, и т.п.

Типичные повторяемые: `Постобработка_Диапазон`, `Постобработка_Строка`, `Постобработка_xml`, `Финальная_обработка`, `ВПР`, `объединить_листы_в_один`, `разделить_листы`, `Ячейка_В_Столбец`, `Добавить_в_карту_переменных`.

Параметр с пустой колонкой A (пустая/служебная строка) — v1: **не копировать** как параметр; если в выделении только такие — сообщение «нет строк параметров»; если смесь с валидными — копировать только валидные **или** отменить весь прогон (выбрать один вариант и зафиксировать в чеклисте; рекомендация: копировать только строки с непустым A из каталога / известным именем).

Строки с отключённым параметром (`__Имя`) — копировать **как есть** (с префиксом `__`), если имя после канонизации имеет `multi_row=True`.

### A.4. Выделение

- Непрерывный блок строк — обязателен.
- Дискретный мультиселект (Ctrl+клик по разным строкам): **v1** — либо поддержать (копировать в порядке сверху вниз одним блоком вставки), либо отказать сообщением «выделите непрерывный диапазон строк». Рекомендация v1: **поддержать** упорядоченный список строк выделения Calc (`getRows` / controller selection), вставка одним непрерывным блоком из N строк.
- Выделение целых столбцов / всего листа — не цель; ограничить разумным максимумом (напр. ≤ 100 строк за раз) с сообщением при превышении.

### A.5. Сообщения пользователю

| Ситуация | Текст (смысл) |
| -------- | ------------- |
| Уникальный параметр | «Параметр «Режим» должен быть в одном экземпляре — копирование отменено.» (подставить фактическое имя; при нескольких уникальных в выделении — перечислить кратко) |
| Не лист параметров | «Активный лист не является листом параметров сбора.» |
| Нет строк для копирования | «Нет строк параметров для копирования.» |
| Слишком много строк | «Слишком много строк (макс. N).» |
| Успех | Опционально короткий toast/не модально; достаточно тихого успеха или одной строки в status. Модальный успех **не** обязателен. |

Сообщения — MsgBox / существующий UI-хелпер проекта; без traceback пользователю.

### A.6. Пустые строки снизу (без лишнего insert)

Строка считается **пустой для вставки**, если во всех значимых колонках параметров нет текста (A и value-колонки B…; объединённый комментарий учитывать по правилам листа).

Алгоритм:

1. `need = N` (число копируемых строк).
2. Считаем `free` = число подряд пустых строк начиная с `insert_at` вниз, пока не встретим непустую или конец разумного скана.
3. Если `free >= need` — писать копии в `insert_at .. insert_at+need-1` без `insertByIndex`.
4. Иначе `insertByIndex(insert_at, need - free)` (или `need`, если политика «всегда вставлять полный блок и сдвигать» — **предпочтительно вставлять ровно `need` строк в `insert_at`**, если любая из целевых ячеек занята; упрощённый вариант v1: если `free < need` → вставить `need` строк в `insert_at`, затем записать; пустые «хвосты» ниже уедут вниз).

**Инвариант:** существующие непустые строки параметров **не затираются**.

## Часть B. Визард ВПР — UX, диапазоны, полное соединение

### B.0. Контекст

Диалог: `show_vlookup_param_dialog` в `param_wizard.py`.  
Сохранение: JSON в C (предпочтительно) и/или legacy B–F.  
Исполнитель: ветка ВПР в `collect_workbooks.py` / lib (`lm` vlookup).

Текущие поля сторон (упрощённо): `left|right`: `sheet`, `start_row`, `start_col`, `header_row`; плюс ключи, `extract_columns`, опции F (цвет, дубли, не найдено, мульти, суффикс `_R`).

### B.1. Баг: раскраска колонок 4–5 при отключённом legacy

**Симптом:** при работе в JSON-режиме / когда параметры ВПР не пишутся в отдельные ячейки B–F, визард (или запись на лист или включение отключение параметра макрос) **всё равно красит колонки D–E (4–5)** строки заголовков листа параметров, даже если в этих ячейках нет значений / заголовков под legacy.

**Причина (ожидаемая):** наследие режима «сохранение в разные ячейки» B–F — оформление заголовков «Ячейка D/E» осталось в коде записи/восстановления шапки.

**Требование:**

1. Не применять legacy-раскраску / подписи колонок 4–5 (и прочих B–F), если активен JSON-only путь записи ВПР **или** если соответствующие ячейки шапки не должны нести метки ВПР.
2. Опираться на уже существующий `_restore_param_sheet_header_row` / `_is_vlookup_param_col_header`: после OK визарда и при открытии листа шапка должна быть «Значение N», а не «Ячейка B/C/…».
3. Регрессия: legacy-запись B–F (если ещё поддерживается) по-прежнему может оформлять B–F **только когда реально пишется B–F**.

### B.2. Убрать legacy-подписи «Ячейка F» и т.п. с формы

На **форме диалога ВПР** убрать пользовательски видимые названия вида «Ячейка B/C/D/E/F» — это наследие колонок листа, не смысл полей.

Заменить на смысловые подписи (см. §B.4–B.6). Внутренние имена контролов в коде могут остаться (`CellFEd` и т.д.) — наружу только русские смысловые label.

### B.3. Диапазоны левой и правой таблицы

#### B.3.1. Было

Отдельно (для каждой стороны): начало строки, начало столбца, строка заголовков (и связанные поля в одном «столбце» формы).

#### B.3.2. Стало

Два параметра **в одном ряду**:

| UI-подпись | JSON (предложение) | Смысл |
| ---------- | ------------------ | ----- |
| **Лев.диапазон** | `left.range` (строка) | Диапазон левой таблицы |
| **Прав.диапазон** | `right.range` (строка) | Диапазон правой таблицы |

Поле **листа** (`left.sheet` / `right.sheet`) сохраняется как сейчас (combo листов).

#### B.3.3. Семантика `range`

| Значение | Поведение |
| -------- | --------- |
| Пусто / не задано | Как **сейчас**: авто-диапазон used-area (или текущая эвристика исполнителя); строка заголовков — авто / из прежней логики |
| Явный A1 | Использовать указанный диапазон; **строка заголовков = первая строка** этого диапазона |

Поддерживаемые формы явного диапазона (v1):

- прямоугольник: `C2:F40`;
- полоса строк: `1:200` / `2:50`;
- полоса столбцов: `D:H`;
- при необходимости одна ячейка как вырожденный случай — вне фокуса; можно отвергать валидацией.

При явном `range` поля `start_row` / `start_col` / `header_row` в JSON:

- либо **вычислять и записывать** для обратной совместимости исполнителя;
- либо исполнитель понимает `range` напрямую и игнорирует тройку, если `range` непуст.

**Рекомендация:** при сохранении из визарда, если `range` задан — заполнять derived `start_row`, `start_col`, `header_row` (+ при возможности конец), чтобы старый код ВПР не ломался; при чтении — если есть `range`, показывать его в UI и считать источником истины.

Legacy JSON без `range` (только start_*/header_row) — открывать в визарде: поля диапазона пустые или собранные в A1 для удобства; поведение сбора без изменений.

### B.4. Тип соединения

На место, освободившееся от блока «Начало строки / столбец / …» (в том же визуальном ряду / зоне), добавить:

| UI | Код JSON | Default |
| -- | -------- | ------- |
| **Тип соединения** | `join_type` | `left` (или пусто ≡ left) |

Значения:

| Код | Подпись UI | Смысл |
| --- | ---------- | ----- |
| `left` / `""` | Левое соединение | Текущее поведение: строки **левой** таблицы + столбцы с **правой** (`extract_columns`) |
| `full` | Полное соединение | Два прохода: как left **и** симметрично для правой таблицы (строки правой + столбцы с левой) |

Нормализация: `левое` / `left` / `left_join` → `left`; `полное` / `full` / `full_outer` / `полное_соединение` → `full`.

Нижележащие контролы формы **подтянуть вверх** на освободившееся место (без больших пустых дыр).

### B.5. Колонки извлечения при полном соединении

| Было | Стало |
| ---- | ----- |
| «Столбцы (E)» / extract с правой на левую | **«Колонки в Лев. из Прав. (←)»** — JSON: `extract_columns` (как сейчас) |

Если `join_type=full`, **под этим** рядом появляется такой же набор контролов на целый ряд:

| UI | JSON |
| -- | ---- |
| **«Колонки в Прав. из Лев. (→)»** | `extract_columns_right` (новый список токенов столбцов; тот же UX columns_pick / список, что у extract) |

При `join_type=left` блок `extract_columns_right` скрыт; в JSON можно не писать или писать `[]`.

Семантика полного соединения (исполнитель):

1. Выполнить текущий ВПР (left ← right) по ключам / `extract_columns`.
2. Выполнить зеркальный ВПР (right ← left) по тем же правилам ключей (keys_left/keys_right меняются ролями) и `extract_columns_right`.
3. Согласовать порядок/место вставки строк и подсветку новых колонок с существующей политикой дублей / мульти / not_found (зафиксировать в реализации: сначала left-pass, затем right-pass на уже расширенном листе **или** построение полного результата в один проход — выбрать один алгоритм и описать в журнале).

**Рекомендация v1 алгоритма:** два последовательных прохода тем же ядром ВПР: (1) left-base + extract from right; (2) right-base + extract from left на целевом листе результата (или временных областях) с теми же опциями F. Детали слияния строк full outer (строки только справа без ключа слева) — обязательно: строки, отсутствующие слева, должны появиться (полное соединение ≠ два независимых left join без union ключей).

### B.6. Нижняя зона опций (бывшая «ячейка F»)

| Было (смысл) | Стало |
| ------------ | ----- |
| Контрол «Ячейка (F)» / куча опций в одной строке | Контейнер / группа **«Итоговые параметры»**: ширина как у контрола «Не найдено»; **высота ≈ +70%** к текущей высоте «Не найдено» |
| Кнопка «Суффикс _R» | Перенести **ниже** кнопки «Дубли»; размер как у «Дубли» |
| Пресет цвета | Подпись **«Цвет для новых колонок»**; ширина самого combo/пресета **≈ ÷2** |
| «Не найдено» | **«Значение для не найдено»** (семантика прежняя: `#Н/Д`, `_ПУСТО_`, …) |

Прочие флаги (Дубли, Мульти, trim ключей и т.д.) — сохранить; сдвинуть layout компактно после удаления legacy-подписей и объединения диапазонов.

### B.7. Совместимость JSON / legacy B–F

| Режим | Требование |
| ----- | ---------- |
| JSON в C | Писать `left.range` / `right.range`, `join_type`, `extract_columns`, `extract_columns_right` (если full); derived start/header при необходимости |
| Чтение старого JSON | Без `range` / без `join_type` → поведение left как сейчас |
| Legacy B–F | Если ещё пишется: кодировать диапазоны и join в существующие слоты **или** только JSON для новых полей (full join / range) — **новые возможности full + range допускается только в JSON**; legacy B–F не обязан выражать full join (при попытке сохранить full в legacy — предупреждение и принудительный JSON / отказ) |

## C. Общий порядок работ и риски

1. Сначала **B.1** (баг шапки) — быстрый win, меньше сюрпризов при ручных тестах.
2. Макрос копирования строк (**A**) — независим от ВПР; можно параллелить с B.
3. Диапазоны + join_type + extract_right + исполнитель full (**B.3–B.5**) — ядро семантики.
4. Косметика нижней зоны (**B.6**) и docs.

Риски:

- full join на больших таблицах — время/память; в журнале писать размеры и длительность;
- неоднозначность A1 `1:200` на листе с несколькими таблицами — в v1 трактовать как строки used-area по ширине листа/колонок стороны;
- копирование строк PP с одинаковым JSON — пользователь сам правит; не делать авто-уникализацию.
