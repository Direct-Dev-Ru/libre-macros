# Research notes: DLP-анализ содержимого (file_list / мини-DLP)

**Контекст:** сейчас реализован только анализ имён/путей (`dlp_analyze_names`). Флаг `dlp_analyze_content` в UI задизейблен. В проекте уже есть бандлы `openpyxl` / `odfpy`, UNO-обход для подсчёта страниц PDF/Writer/Impress (`file_list_macro.py`). OCR/бандла для картинок нет.

**Цель расширения:**  
1) текст из «всех» текстовых и офисных файлов (MS + LO);  
2) картинки/грифы на первых ~3 страницах (PDF, офис) по паттернам «конфиденц», «коммерческая тайна» и т.п.

---

## 1. Текстовые файлы и кодировки

### Сложности
- Одна «правильная» кодировка не существует: файл может быть UTF-8 / UTF-8-BOM / UTF-16 LE|BE / Windows-1251 / CP866 / ISO-8859-5 / mixed.
- Короткие файлы и двоичный мусор ломают эвристики.
- «Успешный decode» ≠ правильный смысл (`latin-1` декодирует почти всё).
- Большие логи: нельзя читать целиком в память без лимита (cap по байтам/символам для DLP).

### Как определять кодировку (практика)
| Подход | Плюсы | Минусы |
|--------|--------|--------|
| BOM → сразу UTF-8/16/32 | Надёжно | BOM часто нет |
| Попробовать UTF-8 strict | Быстро | Не ловит cp1251 |
| `charset-normalizer` (pure Python) | Хорош для RU, бандлится | Размер/зависимость |
| `chardet` (pure Python) | Классика | На кириллице слабее normalizer |
| Каскад: utf-8 → cp1251 → cp866 → utf-16 | Без зависимостей, типично для РФ | Ошибки на экзотике |
| Системная locale / `sys.getfilesystemencoding` | Иногда совпадает | Не про содержимое файла |

**Рекомендация для макроса:** каскад + опционально забандлить `charset-normalizer` (предпочтительно `chardet`). Оценка уверенности; при низкой — помечать `encoding=uncertain` в логе DLP, всё равно сканировать лучший кандидат. Лимит: первые N МБ / M символов.

Форматы «текстовые»: `.txt .csv .tsv .log .md .json .xml .html .htm .ini .cfg .yml .yaml .sql .py .js …` + «unknown» с высокой долей printable.

## 2. Офисные документы — извлечение текста

### Writer / Word
| Формат | Путь извлечения | Сложности |
|--------|-----------------|-----------|
| `.docx` | ZIP → `word/document.xml` (+ headers/footers) | Чистый zip+xml, без LO |
| `.odt` | ZIP → `content.xml` (уже есть `odfpy`) | Стили/frames; текст в разных узлах |
| `.doc` / `.rtf` | UNO Hidden+ReadOnly или антикварные парсеры | `.doc` без UNO почти нереален в pure Python |
| `.fodt` | XML целиком | Большие файлы |

### Calc / Excel
| Формат | Путь | Сложности |
|--------|------|-----------|
| `.xlsx` / `.xlsm` | уже `openpyxl` | sharedStrings, много листов, формулы vs cached value |
| `.ods` | `odfpy` | Аналогично |
| `.xls` | UNO→xlsx (как в collect) или пропускать | Медленно |
| `.csv` | как текст + кодировка | Разделители |

### Слайды / Draw
`.pptx` / `.odp` / `.odg` — XML в ZIP или UNO; для DLP имён грифов полезны, но объём работы отдельный.

### Общие сложности офиса
- **Пароли / DRM** — открытие падает; нужен skip + warning.
- **Производительность** — UNO на каждый файл (как page count) = минуты/часы на больших деревьях; offline-парсеры (zip/xml/openpyxl/odf) на порядки быстрее.
- **AO/LO Python** — нативные `.so`/бинарники бандлить нельзя так же легко, как pure-Python; UNO доступен только внутри офиса.
- **Дубли текста** — колонтитулы, скрытые листы, comments, revisions — решать политикой «что входит в haystack».
- **Ложные срабатывания** — слово «секрет» в шаблоне договора на каждом файле.

**Рекомендуемая стратегия текста:**  
1) offline: docx/odt/xlsx/ods/pptx(+xml);  
2) UNO fallback: doc/xls/сложные/битые;  
3) единый пайплайн: `extract_text(path) → str` → те же regex, что для имён (`coerce_dlp_pattern`).

## 3. PDF — текст

### Сложности
- «Текстовый» PDF vs scanned (картинка страницы) — во втором текста нет.
- Кодировки CID/ToUnicode, кириллица часто ломается в простых экстракторах.
- Шифрование, XFA, портянки на 1000+ страниц.
- Pure-Python: `pypdf` / `pdfminer.six` — бандлятся условно (зависимости); скорость/качество разные.
- Альтернатива в экосистеме макроса: UNO экспорт в текст / Draw — медленно, но единообразно с page count.

### Практичный план
- Сначала извлечь текст со стр. 1…K (K=3–5) лёгким парсером.
- Если текст почти пуст → кандидат на OCR/«image-only PDF».
- Не открывать весь PDF в память без потокового/постраничного API.

## 4. Картинки и «грифы» на первых страницах

### Откуда брать картинки
| Источник | Как | Без OCR даёт |
|----------|-----|----------------|
| PDF | рендер стр. 1–3 → PNG/BMP | нужна библиотека рендера или UNO export |
| DOCX/ODT/XLSX/ODS | ZIP: `word/media/*`, `Pictures/*`, `xl/media/*` | факт наличия картинок + сырые байты |
| Встроенные OLE | сложно | часто пропускать v1 |

**UNO-путь (уже близко к проекту):** открыть Hidden → экспорт первых 3 страниц в графику (PDF/Writer) → файлы во temp → анализ. Минус: очень медленно и хрупко в headless/AO.

### Распознавание грифа «конфиденциально / коммерческая тайна»
Это по сути **OCR + (опционально) детекция штампа**, не «просто regex по пикселям».

| Подход | Pure Python bundle? | Качество RU штампов | Размер |
|--------|---------------------|---------------------|--------|
| **Tesseract** (`pytesseract` + бинарник) | Нет (нужен native `tesseract` + `tessdata` rus) | Хорошее при нормальном DPI | Средний, но не «в pythonpath» |
| EasyOCR / PaddleOCR | Нет (torch/paddle, сотни МБ–ГБ) | Хорошее | Неприемлемо для макроса |
| `pure-python` OCR «из коробки» | Почти нет зрелых для кириллицы | Слабое | — |
| Template matching (OpenCV) | OpenCV не pure Python | Только на заранее известные штампы | Тяжело |
| Цветовые эвристики (красная рамка/угол) | Да (простой код) | Много FP/FN | Малый |

**Вывод по бандлу «на чистом Python»:**  
бесплатной качественной OCR-библиотеки, которую разумно **забандлить в `pythonpath` макросов LO/AO для кириллических грифов**, по сути **нет**. Реалистичные варианты:

1. **Опциональный внешний Tesseract** (пользователь ставит в систему; макрос вызывает, если найден) — лучший баланс.  
2. **Только extract embedded images + метаданные** (есть картинка на doc / на стр. 1–3) без чтения текста грифа — слабый DLP-сигнал.  
3. **Полуручной**: сохранить превью первых страниц в папку `*_DLP_images` для аудитора.  
4. Долгосрочно: отдельный sidecar-сервис вне макроса.

Для штампов важны: DPI ≥ 150–200, предобработка (contrast/grayscale), whitelist зоны (угол листа / колонтитул), словарь OCR ≈ тот же CSV DLP.

## 5. Архитектура, вписывающаяся в текущий мини-DLP

```
имя/путь (есть) ──► regex dict
                      │
содержимое (план) ──► extractors by ext ──► text haystack ──► те же regex
                      │
картинки (план) ──► page1..3 render / zip media ──► [optional OCR] ──► regex
                      │
лог *_DLP: паттерн | источник(match:name|content|image) | копия строки файла
```

Расширения лога (имеет смысл сразу заложить):
- колонка `Источник` = `name` | `content` | `image_p1` …
- колонка `Кодировка` / `Extractor` / `Confidence`

Словарь содержимого — отдельный CSV/JSON (как в UI: `dlp_content_dict_path`), можно частично совпадать с name-dict.

Лимиты обязательны: max file size, max chars, timeout на файл, skip network/locked, blacklist `.exe .dll .zip` (или zip только как контейнер офиса).

## 6. Риски и «подводные камни» внедрения в libre-macros

1. **Время**: content+OCR на дереве каталогов убивает UX; нужен прогресс (уже есть status) + «только маски» + depth.  
2. **AlterOffice filter / pythonpath**: тяжёлые native deps не ставить в entry-скрипт; только `pythonpath` + optional external.  
3. **Лицензии**: Tesseract (Apache 2) ок; следить за tessdata.  
4. **Ложные срабатывания** на шаблонах, копирайтах, слове «password» в open-source.  
5. **Секреты в макросе**: DLP-лог сам становится носителем чувствительных путей/фрагментов — политика хранения.  
6. **Параллельность**: UNO не thread-safe; только последовательный обход.  
7. **Windows Owner vs content**: ортогональные фичи; content не зависит от Owner.

## 8. Ответы на ключевые вопросы «в лоб»

**Как определить правильную кодировку?**  
Не «правильную», а **наиболее правдоподобную**: BOM → UTF-8 → `charset-normalizer`/каскад cp1251/cp866 → confidence; при сомнении — флаг в логе.

**Можно ли на pure Python забандлить OCR грифов?**  
Для кириллических штампов — **практически нет** приемлемого по качеству/размеру варианта. Бандлить имеет смысл экстракторы текста и, опционально, вызов системного Tesseract.

**Анализ «по тексту» vs «по картинкам»?**  
Сначала текст (высокий ROI). Картинки — второй контур: сначала наличие/превью, OCR — optional и только первые 3 страницы.

**Связь с текущим кодом**  
- Имена: `libre_macros_file_list_lib.match_entry_dlp_patterns` / CSV-словарь.  
- Страницы UNO: `uno_count_document_pages` — паттерн для медленного content/image path.  
- Офис offline: `openpyxl_bundled` / `odf_bundled`.
